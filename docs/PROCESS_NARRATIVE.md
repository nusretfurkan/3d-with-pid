# Process narrative

The process description (`description.json`, `description.html`) opens with a readable narrative of the modelled flow; the detailed item report follows it unchanged. Code: `skid/drafting/narrative.py`. Tests: `tests/test_process_narrative.py`, `tests/test_flow_paths.py`. The rest of the description is covered in [drafting](DRAFTING.md#process-description). Source is authoritative.

## Provenance

- Generated by the normal drafting build from the same snapshot as every other output. It has no own revision or digest: `description.json` `source_revision`/`input_digest` and the HTML `<body>` data attributes identify it.
- Deterministic; no model or network call.
- Every mention is a stable ID resolved to the current tag in the same build, so renames, undo and insertions appear immediately.

## JSON

`process_narrative` is a list of paragraph records with the `{text, parts, refs}` shape used by `purpose` and item `function`, plus:

| Field | Meaning |
| --- | --- |
| `role` | `flow` (first run), `path` (another start joining earlier items), `separate` (a group not connected to earlier items), `circuit` (a further declared flow circuit of an item already described, sharing no line with the flow above), `loop` (a run starting on a closed loop fed only by items told later), `branch` (a further outlet of an item already described), `scope` (closing paragraph) |
| `run` | The `flow_sequence` run number, or `null` for `scope` |

The field is additive: other description fields are unchanged and the description adapter version stays `0.2.0`.

## Grounding rules

| Statement | Source |
| --- | --- |
| Order, branches, merges, loops, separate groups | Flow-graph runs over port connectivity (`skid.drafting.graph.FlowGraph`), never tags or coordinates. |
| Declared circuits | A composed item's `flow_paths`: flow entering a declared inlet continues only from that pair's outlet; a second circuit is never called a merge, branch or loop; ports outside every pair are stated as such. Marked as authored definition claims. |
| Pump suction and discharge | Incoming and outgoing lines of a `centrifugal_pump`; "end-suction" only when the template inlet faces along the shaft away from the motor. |
| Vertical or horizontal tank | Template body axis rotated by the placement; no orientation word for an unplaced or tilted item. |
| Top, bottom or side nozzle | Built-in template nozzle axis rotated by the placement; not used for inline valve ends or for composed equipment. |
| Tank dimensions and outlet height | Entity parameters, "(assumed)" when the parameter cites an assumption; outlet height "above the shell base" only for a side outlet on an upright placed shell. |
| Check valve | Permits flow in the drawn direction; intended to prevent reverse flow. |
| Isolation valve | Kind only; never called manual or automatic, because no operator is modelled. |
| Indicators | `observes` relation, always described as a conceptual observation, not a control loop. |
| Composed equipment | Declared name and function, quoted and marked "authored, not verified". |
| Scope end | `boundary` items; a sink without a boundary is stated explicitly. |
| Unresolved placement or open ports | Stated on first mention; unconnected items are listed as not connected, never as a start or end. |

The closing paragraph states that fluid, duty, operating conditions, valve operators and normal valve positions are not modelled. An empty model reads "The model contains no process items with ports, so no flow can be described."

## HTML

Order: header, basis notice, pending warning (when present), `<section class="narrative">` with one `<p data-role="narrative">` per paragraph, then `<details id="item-details">` (closed at first) containing purpose, flow, items, unknowns, open items, registers, manual notes and conflicts with their original anchors, then the footer.

Narrative tags link to `#item-<id>` anchors; in a standalone file, fragment navigation opens the details and scrolls to the item. In the browser workspace the description is shown in a sandboxed `srcdoc` iframe under a CSP that blocks `<base>`. At embed time only, `web/js/documents.js` removes any `<base>` and rewrites same-document `#…` links to `about:srcdoc#…` on the sanitized copy. Exported files keep plain fragments. `tests/browser/description.e2e.mjs` checks both.
