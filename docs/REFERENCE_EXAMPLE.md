# Reference example: the prototype pump skid

The repository ships one persisted example, `examples/pump_skid.json`, generated by `examples/make_fixture.py`. Every dimension, placement and route in it is an **illustrative prototype assumption**, recorded in the assumption map. It exercises the software; it is not a design.

## What the example contains

Process order (from the fixture's connections): `TK-101 → L-101 → HV-101 → L-102 → P-101 → L-103 → NRV-101 → L-104 → HV-102 → L-105 → OUT-101`. LI-101 (tank level) and PI-101 (pump discharge pressure) are conceptual indications linked by `observes`, not process connections.

Counts read from `examples/pump_skid.json` (project `project-pump-skid`, revision 0, empty history, no `name`):

| Section | Records |
| --- | --- |
| `model.entities` | 8 (1 tank, 1 centrifugal pump, 2 isolation valves, 1 check valve, 1 boundary, 2 indicators) |
| `model.ports` | 10, all required, DN50, liquid service |
| `model.connections` | 5 (L-101 … L-105), DN50, outside diameter 0.0603 m |
| `model.assumptions` | 12 |
| `pid.symbols` / `pid.edges` | 8 / 5 |
| `physical.placements` / `physical.routes` | 8 / 5 |

| `asm-isolation-valve-dimensions` | Face to face 0.16, body diameter 0.10 |

| `asm-indicator-dial` | Conceptual 0.08 dial |
| `asm-boundary-marker` | 0.2 marker; downstream plant out of scope |
| `asm-dn50-liquid-service` | All ports DN50, liquid service |
| `asm-dn50-pipe` | All lines DN50, outside diameter 0.0603 (not a pipe schedule) |
| `asm-skid-layout` | Deck top z = 0; flow along +x at y = 0, turning toward −y after the check valve; placement origins listed in the record |
| `asm-indicator-mounts` | Level indication at the tank top centre, pressure indication on the discharge line; no tapping or hookup |
| `asm-guided-routes` | Orthogonal centreline routes for four lines; no fittings, supports, slope or clash checks |
| `asm-manual-route` | Manually chosen pump-discharge route (L-103) above the motor, to exercise manual-route preservation |

Some assumption `source` strings read "docs/PUMP_SKID.md prototype value" or "E1a fixture choice". [PUMP_SKID.md](PUMP_SKID.md) is included as a concise portable summary of the original prototype basis that those strings cite. "E1a fixture choice" labels a value the fixture's author chose when first building it; "E1a" names that initial authoring step, not a separate document, and PUMP_SKID.md lists which values it covers. In both cases the value itself is fully stated in the assumption's `description`. Neither label is independent engineering evidence: these are prototype assumptions that exercise the software ([fixture provenance](FIXTURE_PROVENANCE.md)).

The fixture also includes one manual P&ID choice: symbol `sym-check-valve` and edge `edge-discharge-1` are `manual: true`, which lets the tests check that manual layout survives regeneration.

### Explicitly unknown

The fixture states that the following are **unknown**: duty, flow, pressure, temperature, material and wall thickness. Operating and safety design are omitted. Valve operators are unspecified, so the generated description does not call the valves manual. No instrument tapping, hookup or support is modelled. Nothing in the example is a vendor selection, a vessel or pump design, a plant layout, or a fabrication specification.

## Hands-on edits (standard library only)

Run from the repository root with any Python 3.12 environment; no CAD packages are needed ([getting started](GETTING_STARTED.md)). Everything is written under a fresh `work/reference-manual/` subdirectory, so this walkthrough does not touch `work/skid.json` from [getting started](GETTING_STARTED.md#3-core-standard-library-only). `sample` refuses an existing target (exit 4): to run the walkthrough again, remove `work/reference-manual/` or change the directory name in every command.

<!-- check:pump:start -->
```sh
mkdir -p work/reference-manual
python -m skid.cli sample work/reference-manual/skid.json                                    # copy of the fixture; never overwrites
python -m skid.cli validate work/reference-manual/skid.json; echo "exit $?"                  # VALID, exit 0
python -m skid.cli rename work/reference-manual/skid.json ent-pump P-201 --expected-revision 0   # revision 1; the ID is unchanged
python -m skid.cli rename work/reference-manual/skid.json ent-pump P-201 --expected-revision 1   # "no change": no new revision
```

A typed parameter edit with its own provenance. Applying the same file twice shows the revision check: the second attempt is stale and nothing is written.

```sh
cat > work/reference-manual/motor.json <<'EOF'
{"id": "cmd-motor-length-1", "expected_revision": 1, "type": "set_parameter",
 "payload": {"entity_id": "ent-pump", "name": "motor_length",
             "quantity": {"value": 0.42, "unit": "m", "assumption_id": "asm-user-motor-length"}},
 "assumptions": {"asm-user-motor-length": {
   "description": "User-requested illustrative motor length of 0.42 m; not a vendor selection.",
   "source": "reference walkthrough"}}}
EOF
python -m skid.cli apply work/reference-manual/skid.json work/reference-manual/motor.json                      # revision 2
python -m skid.cli apply work/reference-manual/skid.json work/reference-manual/motor.json; echo "exit $?"      # stale_revision, exit 4
```

Move the pump's P&ID symbol. Physical placement is untouched. The manual L-103 diagram path is **not** rewritten: it becomes `needs_reroute` with its points preserved until you supply a new path.

```sh
cat > work/reference-manual/move-symbol.json <<'EOF'
{"id": "cmd-move-pump-symbol-1", "expected_revision": 2, "type": "move_symbol",
 "payload": {"symbol_id": "sym-pump", "x": 360.0, "y": 320.0, "rotation_deg": 0.0}}
EOF
python -m skid.cli apply work/reference-manual/skid.json work/reference-manual/move-symbol.json                # revision 3; edge-discharge-1 needs_reroute

cat > work/reference-manual/edge-l103.json <<'EOF'
{"id": "cmd-edge-l103-1", "expected_revision": 3, "type": "set_diagram_route",
 "payload": {"edge_id": "edge-discharge-1", "points": [[360.0, 292.0], [360.0, 220.0], [464.0, 220.0]]}}
EOF
python -m skid.cli apply work/reference-manual/skid.json work/reference-manual/edge-l103.json                  # revision 4; diagram current again
```

Move the pump physically. Both incident routes become `needs_reroute`; their old points are kept, and no route is invented. The diagram is unaffected.

```sh
cat > work/reference-manual/move-pump.json <<'EOF'
{"id": "cmd-move-pump-1", "expected_revision": 4, "type": "move_equipment",
 "payload": {"entity_id": "ent-pump",
             "placement": {"position_m": [1.7, 0.0, 0.0], "rotation_deg": [0.0, 0.0, 0.0],
                           "status": "placed", "manual": true, "assumption_id": "asm-user-pump-move"}},
 "assumptions": {"asm-user-pump-move": {
   "description": "Pump moved 0.2 m along +x for the walkthrough; illustrative layout only.",
   "source": "reference walkthrough"}}}
EOF
python -m skid.cli apply work/reference-manual/skid.json work/reference-manual/move-pump.json                  # revision 5
python -m skid.cli validate work/reference-manual/skid.json; echo "exit $?"                  # exit 3: L-102 and L-103 need rerouting
```

Supply both routes in one batch, which is one revision and one undo step. Each route is screened against the conservative equipment-body boxes before it is accepted.

```sh
cat > work/reference-manual/reroute-pump.json <<'EOF'
{"id": "cmd-reroute-pump-1", "expected_revision": 5, "type": "batch", "payload": {"operations": [
  {"type": "set_route",
   "assumptions": {"asm-user-pump-routes": {
     "description": "Suction and discharge runs re-chosen after the pump move; no support, stress or fabrication check.",
     "source": "reference walkthrough"}},
   "payload": {"connection_id": "conn-suction-2", "points_m": [[0.88, 0.0, 0.2], [1.375, 0.0, 0.2]],
               "mode": "manual", "assumption_id": "asm-user-pump-routes"}},
  {"type": "set_route",
   "payload": {"connection_id": "conn-discharge-1",
               "points_m": [[1.7, 0.0, 0.5], [1.7, 0.0, 0.7], [2.21, 0.0, 0.7]],
               "mode": "manual", "assumption_id": "asm-user-pump-routes"}}
]}}
EOF
python -m skid.cli apply work/reference-manual/skid.json work/reference-manual/reroute-pump.json               # revision 6
python -m skid.cli validate work/reference-manual/skid.json; echo "exit $?"                  # VALID, exit 0
```

Undo and redo are new revisions. The revision counter keeps increasing, and the content returns exactly.

```sh
python -m skid.cli undo work/reference-manual/skid.json --expected-revision 6                 # revision 7: routes pending again
python -m skid.cli validate work/reference-manual/skid.json; echo "exit $?"                  # exit 3
python -m skid.cli redo work/reference-manual/skid.json --expected-revision 7                 # revision 8: routes current
python -m skid.cli validate work/reference-manual/skid.json; echo "exit $?"                  # exit 0
python -m skid.cli lists work/reference-manual/skid.json                                      # P-201, motor_length 0.42 m, all routes current
```

## Reference script

`scripts/reference.py` runs a reproducible reference on an isolated copy of the fixture and records what happened:

```sh
python scripts/reference.py --output <new-or-empty-directory>          # core lane, standard library only
python scripts/reference.py --output <new-or-empty-directory> --cad    # core lane + real five-output lane
```

- `--output` must not exist or must be empty. Nothing is overwritten, and nothing is written outside it. `examples/pump_skid.json` is only read. No language model, network service, Blender or user project is involved. `--timeout S` bounds each build (default 900 s).
- **Core lane** (`core/`) runs the real `skid.cli` and `skid.drafting` commands as subprocesses and records their exit statuses: copy, validate, list, overwrite refusal, stale and duplicate-tag refusal, rename → drafting → undo (a new revision) → reload, a nozzle move that leaves the route pending, a P&ID symbol move that leaves physical data unchanged, and repeated drafting of unchanged input. It does not run the 3D/CAD generators or the Blender bundle, and `status` honestly reports `unpublished`.
- **CAD lane** (`cad/`, needs the CAD environment) runs the real interactive service and generators. It checks five complete outputs with one identity and the verified pointer; STEP verification plus an independent reimport; the exact legend and item index; and an unchanged forced rebuild (geometry, source and mappings, not STEP bytes). It also runs rename → rebuild → undo → save → service restart, restoring model, P&ID and physical records; stale and conflict refusals; and a pending nozzle move that keeps the last complete publication. It confirms that the standalone geometry CLI exits `0` with a *pending* manifest, and compares manual route and diagram records exactly.
- The script writes `evidence.json`. That file holds the expected counts from `scripts/reference_expected.json`, every command's argv, exit status, expected status and output tail, every check with its outcome, and SHA-256 hashes of key files. Exit `0` means every asserted contract held, `1` means at least one check failed (all checks still run and are recorded), and `2` means a usage or precondition error, such as `--cad` without CadQuery or a non-empty `--output`.

`scripts/reference_expected.json` records the expected counts for the unchanged fixture. They include 16 legend keys and 13 index items. In the CAD lane they also include 67 STEP parts, 350 solids, 68 display components, 10 port flange faces and 12 envelope checks. These are expectations that the script rechecks, not results.

## Output files

For the interactive workspace, `<stem>.workflow/` beside the project holds one immutable directory per build, `builds/b<UTC timestamp>-r<revision>-<8 hex>/`:

| Artifact | Files |
| --- | --- |
| 3D display | `scene.json`, `display.manifest.json`, `preview/display-NNNN.json` |
| CAD | `model.step`, `geometry.recipe.json`, `cad.verification.json`, `cad.manifest.json` |
| P&ID | `pid.svg`, `drawing.inventory.json`, `pid.manifest.json`, `preview/pid-NNNN.svg` |
| Legend | `legend.svg`, `legend.manifest.json`, `preview/legend-NNNN.svg` |
| Description and index | `description.json`, `description.html`, `item-index.json`, `description.manifest.json` |
| Build records | `snapshot.json`, `request.json`, `result.json`, `events.jsonl`, `worker.log`, `build.json` (seal with per-artifact results and a SHA-256 of every file), optional `manual-notes.json` |

`<stem>.workflow/current.json` is the **only** publication pointer: `{format, build_id, project_id, source_revision, input_digest, status: "complete", build_sha256, published_at}`. It is replaced atomically, and only after the service has rechecked every file from disk. The service also rereads the source under the document lock and confirms the same digest. Failed, pending, cancelled, superseded and source-changed builds never move it. On start-up, reopen and every change, the service rechecks the published build. A tampered or missing file makes `sync.state` `invalid`, and that build is withdrawn from the displayed outputs. Pending builds remain inspectable as labelled working previews.

A real build occupies roughly tens of megabytes, mostly progressive preview snapshots. `--keep-builds N` limits retention, but never deletes the published, running, queued or an unsealed build.

The offline path writes `<stem>.skid/bundles/r<revision>-<key>/` (`pid.svg`, `model.blend`, both manifests, `lists.json`, `snapshot.json`, `bundle.json`) and the pointer `<stem>.skid/current.json`. `python -m skid.cli status` compares it with the source: `synchronized` (exit 0), `pending` (3), `stale` or `unpublished` (4), `bundle_invalid` or `invalid_source` (1).
